Install the observer so RubixKube can see your cluster: what's running, what changed and what breaks. One `kubectl apply` puts it in its own namespace. Your cluster runs the observer, and everything else runs in RubixKube.

## Before you start

- `kubectl` pointed at the cluster. `kubectl get nodes` should work.
- Permission to create a namespace, a ClusterRole and a ClusterRoleBinding.
- Outbound access from the cluster to `api.rubixkube.ai:443`, `nats.rubixkube.ai:4222` and `ghcr.io:443` (the image).
- An admin account in the [console](https://console.rubixkube.ai).

## Install

<Steps>
  <Step title="Copy your command">
    In the console, open **Environments**, click **Connect** and pick **Kubernetes**. Copy the command. It already holds your API key.
  </Step>
  <Step title="Run it">
    ```bash
    kubectl apply -f "https://api.rubixkube.ai/install/observer.yaml?apiKey=rk_YOUR_API_KEY"
    ```

    You should see:

    ```
    namespace/rubixkube-system created
    secret/rubixkube-observer-config created
    serviceaccount/rubixkube-observer created
    clusterrole.rbac.authorization.k8s.io/rubixkube-observer created
    clusterrolebinding.rbac.authorization.k8s.io/rubixkube-observer created
    role.rbac.authorization.k8s.io/rubixkube-observer-leases created
    rolebinding.rbac.authorization.k8s.io/rubixkube-observer-leases created
    service/rubixkube-observer-peers created
    deployment.apps/rubixkube-observer created
    ```
  </Step>
  <Step title="Check the pod">
    ```bash
    kubectl get pods -n rubixkube-system
    ```

    Wait for **STATUS** to show `Running`. If it doesn't, read the logs:

    ```bash
    kubectl logs -n rubixkube-system deployment/rubixkube-observer --tail=20
    ```
  </Step>
  <Step title="Open it in the console">
    The dialog updates by itself and says your cluster is connected, usually within a minute. Add an environment label, then click **Open it**.
  </Step>
</Steps>

## What runs in your cluster

By default, one pod in `rubixkube-system`. It serves its own read-only Kubernetes tools, so no separate MCP server runs.

| | Request | Limit |
|---|---|---|
| Memory | 256Mi | 768Mi |
| CPU | 250m | 1 |

This suits clusters up to about 50 nodes. It runs as a non-root user with a read-only root filesystem and no Linux capabilities.

### Run more than one pod

On a big cluster the source page tells you how many pods to run. Add `&replicas=` to the install address, from 1 to 5:

```bash
kubectl apply -f "https://api.rubixkube.ai/install/observer.yaml?apiKey=rk_YOUR_API_KEY&replicas=3"
```

Or scale it:

```bash
kubectl -n rubixkube-system scale deployment rubixkube-observer --replicas=3
```

With more than one pod, a Lease picks one as leader, and the leader hands each workload to one pod. You can also raise the memory limit instead.

## What the role can do

The observer's ClusterRole, `rubixkube-observer`, reads most of the cluster: pods, nodes, Services, ConfigMaps, workloads, networking, storage, RBAC objects and pod logs. It can also create events.

Two permissions deserve a plain mention. The role has `get`, `list` and `watch` on `secrets`, and `create` on `pods/exec`, so that is what the observer's token can do in your cluster. The observer itself uses less. It watches only the metadata of Secrets, so their contents never reach it, its tools return key names and never values, and no observer code runs `pods/exec`. See [Safety and control](/concepts/guardrails) for how Rubix's actions are limited.

## What the observer watches

| What | Detail |
|---|---|
| Pods | State, restarts, resource use, owners |
| Deployments, StatefulSets, DaemonSets | Replica health and rollouts |
| Services and Ingresses | Which apps they send traffic to |
| Nodes | Status and capacity |
| Events | The cluster's own events |
| ConfigMaps and Secrets | Metadata only, so RubixKube knows when one changed but not what's in it |

Crash loops, out of memory, stuck pods and the other checks are all rules you can change. See [Change what an observer looks for](/using/environments#change-what-an-observer-looks-for). Those settings apply without a restart.

## Upgrade

Run the install command again, copied from the console. It updates the observer in place and keeps the environment, its history and its settings.

```bash
kubectl apply -f "https://api.rubixkube.ai/install/observer.yaml?apiKey=rk_YOUR_API_KEY"
```

If you run more than one pod, keep `&replicas=` on the address. Without it, the apply sets the Deployment back to one pod.

Installs from before observer 1.1.0 also ran a Kubernetes MCP server next to the observer. It's no longer needed. Remove it after the upgrade:

```bash
kubectl -n rubixkube-system delete deploy/kubernetes-mcp-server svc/kubernetes-mcp-server sa/kubernetes-mcp-server
kubectl delete clusterrole,clusterrolebinding kubernetes-mcp-server-readonly
```

Then remove the `kubernetes` entry from the `mcp-config` ConfigMap, or delete the ConfigMap if that was its only entry:

```bash
kubectl -n rubixkube-system edit configmap mcp-config
```

## Add your own MCP servers

The observer reads extra MCP servers from the optional ConfigMap `mcp-config` (key `mcp.json`) in `rubixkube-system`. The install command never overwrites it.

```bash
kubectl -n rubixkube-system create configmap mcp-config --from-file=mcp.json=./mcp.json
kubectl -n rubixkube-system rollout restart deploy/rubixkube-observer
```

```json
{
  "mcpServers": {
    "grafana": { "url": "http://mcp-grafana.monitoring.svc.cluster.local:8000/mcp" }
  }
}
```

Each server's state, connected or failing with the error, shows under **Tools** on the source's page.

## Try it on KIND

The same command works on a local KIND cluster, so you can try RubixKube without touching a real one.

```bash
kind create cluster --name rubixkube-test
kubectl apply -f "https://api.rubixkube.ai/install/observer.yaml?apiKey=rk_YOUR_API_KEY"
```

## Troubleshooting

<AccordionGroup>
  <Accordion title="Pod stuck in ImagePullBackOff">
    The cluster can't reach the image at `ghcr.io/rubixkube-io/observer-agent`. Test it from inside the cluster:

    ```bash
    kubectl run test-curl --image=curlimages/curl -i --rm --restart=Never -- curl -I https://ghcr.io
    ```

    If this fails, a proxy or egress policy is in the way. Allow the three addresses listed under [Before you start](#before-you-start).
  </Accordion>
  <Accordion title="Pod in CrashLoopBackOff">
    Read the logs from the last run:

    ```bash
    kubectl logs -n rubixkube-system deployment/rubixkube-observer --previous
    ```

    If they point at the API key, run the install command again, copied fresh from the console.
  </Accordion>
  <Accordion title="The dialog keeps waiting">
    1. Check that the pod is `Running` with `kubectl get pods -n rubixkube-system`.
    2. Check that outbound TCP to `nats.rubixkube.ai:4222` is open. The observer needs it as well as HTTPS.
  </Accordion>
  <Accordion title="Observer running out of memory on a big cluster">
    Run more pods, as above. The source page says how many. Or raise the limit:

    ```bash
    kubectl edit deployment rubixkube-observer -n rubixkube-system
    ```

    The next install command you run sets the limit back to 768Mi.
  </Accordion>
</AccordionGroup>

## Uninstall

```bash
kubectl delete -f "https://api.rubixkube.ai/install/observer.yaml?apiKey=rk_YOUR_API_KEY"
```

This removes everything the install created, including the namespace. The source stays in the console until you delete it there. An `mcp-config` ConfigMap goes with the namespace.
