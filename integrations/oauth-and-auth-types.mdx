Every connection reaches its tool in one of two ways. With sign-in (OAuth), you approve RubixKube in the tool and never hand over a password. With a token, you paste a key you made in the tool. The console shows the ways each tool accepts, and the first one is the usual choice.

## Sign in with OAuth

Open a tool under **Customize > Integrations** and choose its sign-in button. A new tab opens on the tool. Sign in there and allow RubixKube, then come back. The tool shows as connected on its own.

RubixKube gets an access token you can revoke at any time, here or in the tool. It refreshes that token on its own, so you stay connected.

### The address to allow

Some tools only accept sign-in from an address an admin has allowed. Add this one, once. The console shows it with a copy button.

```text
https://console.rubixkube.ai/oauth/callback
```

| Tool | Where an admin allows it |
|---|---|
| Datadog | **Organization Settings > MCP Server > MCP OAuth Redirect URLs** |
| Atlassian Rovo | **Atlassian Administration > Rovo > Rovo MCP server > Domains**, as `https://console.rubixkube.ai/**` |
| incident.io | **Settings > MCP**. Turn on MCP and add `console.rubixkube.ai` under allowed redirect domains |

A connection made before this address existed keeps its old one and goes on working. To move it, choose **Use the new sign-in address** on the connection.

### Your own OAuth app

When you add a [custom MCP server](/integrations/custom-mcp-servers) with OAuth, RubixKube first asks the server how it signs in. If the server can register RubixKube itself, you have nothing to fill in. Otherwise, or if you choose **Use your own app**, enter a client ID and, if it has one, a client secret. Then give an issuer URL, or the authorization and token URLs, and any scopes. Set your app's redirect address to the one above.

## Use a token

Paste the token in the tool's form. Give it the least access it needs. RubixKube stores it encrypted and uses it only to call that tool.

Tools expect tokens in different forms, and RubixKube sends the right one for each catalog entry, so you paste the token alone.

| Form | Used by |
|---|---|
| `Authorization: Bearer <token>` | Most tools |
| `Authorization: Token token=<key>` | PagerDuty |
| `Authorization: Sentry-Bearer <token>` | Sentry |
| `api-key: <key>` | New Relic |
| `DD-API-KEY` and `DD-APPLICATION-KEY` | Datadog, with an API key and application key |

For your own integrations, the console offers these:

| Sign-in | Custom MCP server | Custom REST API | How it's sent |
|---|---|---|---|
| No sign-in | Yes | Yes | Nothing is sent |
| Token | Yes | Yes | `Authorization: Bearer <token>` |
| API key | No | Yes | `Authorization: Token <key>` |
| Username and password | No | Yes | Stored encrypted |
| OAuth | Yes | No | Handled by sign-in |

## When a connection stops working

| Status | What to do |
|---|---|
| Needs attention | The tool refused the sign-in or token. Choose **Sign in again** or **Replace token** |
| Sign in to finish | The sign-in wasn't completed. Choose **Sign in** |
| Turned off | Choose **Turn back on** |

**Disconnect** stops Rubix using the tool and deletes the saved sign-in.

## Troubleshooting

<AccordionGroup>
  <Accordion title="The tool refuses the redirect address">
    An admin needs to allow `https://console.rubixkube.ai/oauth/callback` in the tool. Check for a trailing slash.
  </Accordion>
  <Accordion title="The connection works but Rubix finds nothing">
    Look at the tool's [Reads section](/integrations/overview#see-what-a-connection-can-read). A refused read shows the tool's own words and the fix.
  </Accordion>
</AccordionGroup>
